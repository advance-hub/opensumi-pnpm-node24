# OpenSumi Server

The product compatibility runtime remains on Node.js 24 and owns OpenSumi RPC, extension hosts, terminals and optional Yjs collaboration. The supported public entry at port `8000` remains Node. The optional Go Workspace Agent is a private child process for migrated OS services. A separate Go WebSocket Gateway also exists; since the artifact-driven default migration (§10.17) it is enabled by default whenever a runnable verified package is present, with `OPENSUMI_WS_GATEWAY_MODE` as the override/rollback switch. Its private Node hop supports one physical `multiplex-v1` transport with isolated logical RPC connections. With 500 idle connections it still uses more whole-tree RSS than Node, but a 10-concurrent-client profile with Gateway-answered file RPCs passed the 25 percent whole-tree memory gate (`-39.43%` at 64 KiB payloads) while large-file reads regress beyond the 10 percent latency gate, so enablement remains workload-shaped: deployments dominated by large-file reads or mostly-idle connections should keep the switch off. Both paths are governed by `docs/architecture/go-workspace-agent-migration.md` (§10.16 for the concurrent re-check, §10.17 for the default migration).

The migration has independent switches. A production artifact built with `pnpm build:server:workspace-agent` automatically makes Watch, Content Search and File Search authoritative in Go when the package matches the current OS/architecture, reports `nativeStartupVerified: true`, passes its checksum, and advertises all three capabilities. A normal Server build without that package remains entirely on Node. `OPENSUMI_WORKSPACE_AGENT_AUTO_MODE=off` disables these package-driven defaults; each `OPENSUMI_WORKSPACE_AGENT_*_MODE=off|shadow-read|enabled` setting remains a stronger per-service override. Content Search and File Search support `shadow-read`; Watch event streams do not. `OPENSUMI_WORKSPACE_AGENT_PATH` can select a packaged binary. Startup and capability failures fall back to Node; an unavailable optional service does not poison the services that the running Agent does provide. A Watcher stream drop moves the current connection to Node and never switches that connection back automatically. An active Content Search stream reports an error instead of replaying partial results; File Search can safely fall back because its bounded result is not exposed until completion. A later request may start a fresh Agent after a 250/1000ms on-demand backoff. Three failures in one minute exhaust the restart budget until the Server restarts, preventing crash loops and duplicate resource owners.

The package-driven default is deliberately narrower than “Go everywhere”: one server-scoped Agent replaces per-connection Node watcher processes and also owns the two search paths that passed their current-source gates. Content Search measured Node P95 at `73/73/72 ms` and Agent P95 at `73/76/74 ms`, or `73 ms` versus `74 ms` across-run medians (`1.37%` regression, below the `10%` limit).

File Search three fresh-process, 20-warmup/200-query runs over this repository measured P95 medians of `17.981 ms` for Node and `14.219 ms` for the Agent (`20.93%` faster). Median post-warmup process-tree growth fell from `89,391,104 B` to `15,155,200 B` (`83.05%` lower); final tree RSS was `26.61%` lower despite the Agent variant starting from a `12.64%` higher idle baseline. This is V8 heap-capacity/high-water avoidance under repeated fuzzy scans, not proof of a JavaScript object leak. An uncapped parity run returned the same 590 paths, and a real production Quick Open displayed both proof files, opened the nested result, reported zero browser errors, and exposed a healthy protocol `1.1` Agent through `/readyz`. Operators can still force `shadow-read` or `off`; remote platform and 50-session evidence remains a rollout-qualification boundary rather than a prerequisite for using a verified local package.

The schema 6 product smoke now also has a no-override auto-rollout mode. With all three service environment variables absent, the current native package was selected automatically; `/readyz` reported all three as `enabled`, the active tree contained one `16,629,760 B` Agent and no Node watcher, Search completed in `582 ms`, Quick Open in `29 ms`, Watch add/delete in `340/367 ms`, and the full crash-recovery/Node-fallback/cleanup sequence passed. A separate one-session Node/Agent capacity smoke measured Content Search P95 at `68/72 ms` and File Search P95 at `27/27 ms`; both latency gates passed, while whole-tree RSS was `9.91%` higher on the Agent run. That single capacity run validates the workload and gates, not a 50-session performance claim.

`OPENSUMI_WS_GATEWAY_MODE=enabled` explicitly requires the Go public ingress and moves Node HTTP plus the Fury/RPC byte stream to private local listeners. Since §10.17 the gateway is also the artifact-driven default: with the variable unset, startup launches the gateway whenever `server/dist/workspace-agent/ws-gateway` carries a valid production manifest for the current platform (dev additionally probes `go/workspace-agent/bin`), and falls back to direct Node sockets with a `fallback:` reason recorded in `/healthz` `wsGateway.error` if the launch fails. Explicit values other than `enabled` — `0`, `off`, `disabled` or anything else — keep the historical direct-socket behavior and are never overridden by an artifact; an explicitly enabled gateway that fails to launch fails startup instead of falling back. `OPENSUMI_WS_GATEWAY_PATH` selects a different binary (the only candidate when set), and `OPENSUMI_WS_GATEWAY_CHANNEL_MODE=multiplex-v1` is the default channel mode: all browsers share one private Gateway-to-Node socket while Node reconstructs independent logical connections; `direct` retains the old one-private-socket-per-browser rollback path. Both modes preserve `/readyz` admission, size/connection limits, heartbeat, write deadlines and physical-close cleanup. Concurrent handshakes share one Node readiness request and cache its result for at most 100 ms; gateway shutdown cancels an in-flight shared check.

When the Gateway experiment is enabled, `OPENSUMI_WS_GATEWAY_FILE_RPC_MODE=enabled` (the default inside that experiment) now terminates compatible `DiskFileService:readFile`, `access`, `readDirectory` and `stat` Fury RPCs directly in Go instead of forwarding them to Node. The typed and Any-protocol codecs are byte-for-byte checked against the current JavaScript serializer. Direct reads accept successful local `file:` reads of regular files up to `WS_GATEWAY_FILE_RPC_MAX_BYTES` (8 MiB by default); access currently accepts the default `F_OK` mode; directory reads preserve the existing empty/partial-result error contract and symbolic-link target types. Stat preserves the current one-level recursive directory shape, symlink target metadata and JavaScript `Date` millisecond rounding. Directory-list responses use the same 8 MiB byte limit, while stat uses the independent `WS_GATEWAY_FILE_RPC_METADATA_MAX_BYTES` limit (1 MiB by default); both stop before an oversized result can accumulate. Parse mismatches, unsupported URI forms and access modes, read errors, oversized results and bursts above `WS_GATEWAY_FILE_RPC_MAX_CONCURRENT` (16 by default) preserve the original request and fall back to Node. `/_opensumi/ws-gateway` exposes per-method read-only counters so product tests can prove which browser work really avoided Node.

The multiplexed mode passed the full production browser smoke, including Search, Quick Open, Watch, Workspace Agent crash recovery, Node fallback and cleanup. At 500 idle connections over three paired runs, handshake P95 was `2.676 ms` versus Node's `2.729 ms` (`1.95%` faster), but whole-tree P95 RSS was `120,586,240 B` versus `93,274,112 B` (`29.28%` higher). A separate same-code direct-mode profile measured `8.464 ms` and `122,437,632 B`; this shows multiplexing removes the direct mode's handshake bottleneck and only marginally changes Gateway RSS, but the large run-to-run V8/Go RSS variance means it is not a memory qualification result. Use `profile:ws-gateway` to reproduce either channel mode. That idle-connection result is the reason mostly-idle deployments should keep `OPENSUMI_WS_GATEWAY_MODE` off; §10.16 later qualified the gateway for multi-session small/medium file RPC workloads, and §10.17 turned it on by default only when a verified package exists.

The expanded Go-owned RPC path also passed the compiled Chromium product gate. The current run directly served `136` real browser file RPCs in Go: `29` reads, `58` access checks and `49` stats (`2,791,702 B` read). This proves stat is a real hot product path; `readDirectory` was not naturally exercised by that UI sequence and remains covered by byte-golden, Gateway no-forwarding and production-channel tests. Search, Quick Open, Watch, three Agent failures, Node fallback, browser cleanup and Server/Gateway shutdown all passed with zero unexpected console/page errors. A separate schema 3 `profile:go-file-rpc` run used five fresh Node/Gateway pairs, each with 20 warmup, 200 timed and 500 stress cycles over read, access, directory-read, file-stat and directory-stat requests. All `18,000` Gateway RPCs avoided Node, and every complete stat object matched Node. Cross-run median P95 improved by `20.41%`, `6.77%`, `22.73%`, `45.40%` and `56.32%` respectively; post-stress Node Server RSS was `13.70%` lower, but the full Server+Gateway tree was only `1.30%` lower. This one-connection result alone could not reverse the prior 500-idle-connection failure; §10.16's 10-concurrent re-check supplied the missing workload shape and §10.17 made the verified package the default.

`/healthz` and `/readyz` include read-only `workspaceAgent` and `extensionHost` diagnostics. The Extension Host view reports active/disconnected hosts, retained browser-service proxies and main-thread connections, the three-session default limit, saturation, the 256 MiB V8 old-space budget and lifecycle counters without exposing client IDs. Host restarts preserve the live browser proxy so later crashes can still request recovery; browser disconnect cleanup removes that proxy even when the Extension Host exited first. At capacity the server only reclaims disconnected or dead hosts; if all three are active, the new host request is rejected instead of evicting an existing session. A host that does not finish its startup handshake in 15 seconds is force-cleaned. Saturation and Agent degradation are deliberately non-gating (`affectsReadiness: false`) so existing sessions remain connected; main-process memory pressure remains the readiness gate.

Per-extension activation diagnostics are opt-in with `EXTENSION_HOST_ACTIVATION_DIAGNOSTICS=enabled`. The default path does not sample process memory or scan the Node module cache and does not expose installed extension IDs. When enabled for an internal capacity run, each host retains at most 64 extension records and health output aggregates only the top 10 without client IDs; all records are removed when the host is disposed. Heap/RSS deltas are process-wide observations during potentially concurrent activation, so use them to rank investigation candidates rather than as causal per-extension accounting. Do not expose an enabled diagnostic endpoint publicly.

The current three-session full-extension diagnostic smoke identified the Git startup cluster as the main observed heap-growth candidate. `vscode-icons` had the longest activation (`2406 ms` on the Node-watcher run), while GitHD and Emmet registered the largest subscription sets (`97` and `43`). These are investigation priorities, not grounds to disable the extensions: all nine reported extensions activated successfully in all three hosts, both Node/Agent variants had zero Extension Host crashes, rejections and startup timeouts, and disposal removed all three hosts and their diagnostic records.

Production extension discovery is isolated from the account running the Server. By default it reads and installs marketplace extensions under `tools/extensions`; set `OPENSUMI_EXTENSION_DIR` to an absolute mounted volume when extensions must persist outside the artifact. Development without this override keeps the framework's existing `~/.sumi/extensions` behavior. This preserves VS Code Node extension support while preventing unrelated host-user extensions from being activated in every production session. Dual-entry extensions that explicitly prefer `extensionKind: ui` run in the existing browser Worker instead of the Node Extension Host; workspace, debugger, terminal and TypeScript-server extensions stay in Node.

Long-lived Node and Worker hosts release stale extension state when an extension is disabled, removed or replaced by another path/version. The host runs deactivation hooks, disposes context subscriptions, drops per-extension API instances and, for Node extensions, removes modules below the old extension real path from the require cache. This prevents install/upgrade cycles from retaining an obsolete extension graph until the whole browser session exits.

Node and Worker hosts also coalesce concurrent activation requests for the same extension. Only one `activate()` call may create the module/context/subscriptions; all concurrent callers share that promise, and the in-flight reference is removed on both success and failure. Extension replacement waits for an in-flight activation before deactivation, and graceful Node-host shutdown waits for activations before disposing subscriptions. The capacity gate requires every reported extension's activation count to equal its reporting-host count, so duplicate activation cannot hide behind a crash-free process count.

The client-lifecycle gate caught and rejected an initial shutdown run where all three Extension Hosts exited but three browser-service proxies remained. The race occurred when host disposal began before the browser close event and cleared the disconnect marker after that event arrived. Cleanup now reads the latest connection state after asynchronous host shutdown; the repeated three-session full-extension run reports exactly three proxies/connections while active and zero hosts, disconnected clients, proxies and main-thread connections after close in both Node-watcher and Workspace-Agent variants. This is a one-run lifecycle smoke, not a replacement for the three-run memory qualification.

Browser-side restart requests are also serialized and policy-coalesced. Concurrent `Always` requests share one transaction; an `Always` request arriving during a `WhenExit` PID check upgrades that transaction; hidden-page requests retain the strongest policy and wait until the page is visible. This prevents crash notifications, visibility recovery and a manual restart from racing into multiple Extension Hosts. A production Chromium session using the full configured VS Code extension directory completed 10 sequential manual restart cycles: `created` advanced from 1 to 11 while `disposed` advanced from 0 to 10, with exactly one active Host, browser-service proxy and main-thread connection after every cycle. Crashes, rejections and startup timeouts remained zero. Sampled whole-tree RSS ranged from `219643904` to `318734336` bytes and Extension Host RSS from `132841472` to `196640768` bytes without monotonic growth. Closing the browser produced `created=disposed=11` and zero active/disconnected Hosts, proxies and connections. This is a one-session restart/reclamation gate, not a multi-session capacity result.

A broader “prefer every declared browser entry” experiment was rejected by the real browser gate. The controlled Emmet and Merge Conflict packages declare browser paths but do not ship those files in the deployed extension directory, producing 12 `Not Found` console errors across three sessions. Production therefore retains the conservative rule: browser-only and explicit `extensionKind: ui` packages may use the Worker; unspecified/workspace dual-entry packages stay in Node until their deployed browser artifact is verified.

The current binary supports macOS, Linux and Windows. macOS builds require CGO and use native FSEvents so recursive repositories do not consume one descriptor per file. Linux uses fsnotify/inotify, while Windows uses fsnotify/`ReadDirectoryChangesW`. Unix hosts use a private `0600` socket. Windows uses a token-authenticated ephemeral IPv4 loopback listener whose allocated port is delivered through the child-process stdout handshake; the adapter rejects non-loopback announcements. The Agent consumes `OPENSUMI_AGENT_TOKEN` before opening its listener and immediately removes it from its process environment, retaining the credential only in the authentication interceptor. Both search services construct an explicit child environment with the credential removed case-insensitively, so ripgrep cannot inherit it even if the Agent is embedded through another entrypoint later.

`build:server:workspace-agent` writes the production binary and `workspace-agent.manifest.json` under `server/dist/workspace-agent`. The manifest records the protocol, services, Go target platform, revision, native-startup verification and SHA-256 digest. Production startup requires the manifest and verifies its schema, protocol, shape, platform, filename and digest before execution; a missing or invalid manifest leaves Node authoritative. Node's `win32` platform is deliberately mapped to Go's `windows` target name. Development may still use an unpackaged `go/workspace-agent/bin/workspace-agent` (or `workspace-agent.exe` on Windows).

The default server does not instantiate AI or collaboration modules. The RPC and collaboration WebSocket servers disable compression by default and enforce payload, connection and buffered-output limits. `TERMINAL_IDLE_TIMEOUT` controls the WebSocket reconnect grace period before a client is disposed. Persistent PTYs then receive a separate bounded resume lease from `TERMINAL_PERSISTENT_SESSION_TIMEOUT` (30 minutes by default); transient, extension-owned and Electron terminals still stop immediately. All limits are configurable with the environment variables documented in `docs/architecture/client-server-runtime.md`.

The three-session Extension Host production smoke passed on both Node Watcher and Go Workspace Agent paths: each run kept exactly three Extension Hosts active, completed Search and Quick Open without unexpected browser errors, and reclaimed all Extension Hosts and terminals after browser close. The smoke also fixed a real concurrent `layout-global.json` write conflict by reloading, merging the pending key update and retrying optimistically. This is a lifecycle result, not a memory-performance qualification: the single Agent run used more Extension Host RSS than the single Node run, so rollout decisions still require repeated same-workload profiles.

The follow-up controlled-extension profile used the complete configured VS Code extension directory, a 20-second post-workload warmup, eight seconds of process-tree sampling, three browser sessions and three fresh runs per variant. Median P95 whole-tree RSS was `504,168,448 B` on Node Watchers and `259,211,264 B` with the Workspace Agent (`48.59%` lower). Content Search was `186 ms` on both paths; File Search was `91 ms` versus `93 ms` (`2.20%` slower, inside the `10%` gate). All six runs held exactly three Extension Hosts, reported three successful creations, zero crashes/rejections/startup timeouts, and reached zero active hosts with three disposals after browser close. The profiler now requires those lifecycle counters, so a crash followed by a fast replacement cannot masquerade as a stable three-process result. This is the accepted three-session product boundary, not a 50-session release qualification.

`profile:runtime` samples the selected PID and all descendants. It classifies known OpenSumi child roles, redacts common command-line credential forms, and emits JSONL samples plus P50/P95/peak summaries. Relative output paths are resolved from the repository root. `compare:runtime` requires three runs per variant by default, compares the median P95 and peak across runs, and reports the 25% whole-tree memory gate. Linux cgroup v2 memory is included when readable; process-tree RSS and cgroup memory have different scopes and should both be retained in capacity reports.

`profile:browser-runtime` is the real-product capacity entrypoint. Start the client and a production server first, then pass the server PID, exact final Search UI result, exact Quick Open file result, variant, session count and run number. It opens real Chromium sessions in bounded batches, executes one setup and one measured warm Content Search plus File Search in every session, samples the complete server process tree, closes the browser and records a post-close process snapshot. Run Node and Agent variants three times at 1, 10 and 50 sessions on an isolated capacity host; do not substitute the logical watcher-multiplexing test for a 50-browser capacity result.

`capacity:workspace-agent` is the qualification supervisor around that profiler. It alternates fresh Node and Agent servers, requires full Extension Host/terminal process counts plus one browser-service proxy and main-thread connection per active browser session, rejects browser errors and watcher fallback, then requires all four Extension Host lifecycle counts to return to zero after browser close. It verifies post-Server cleanup and emits the 25% memory gate plus independent 10% Content Search and File Search P95 gates. Agent runs explicitly enable all three migrated services; Node runs keep all three off. Pass `--extension-dir` to record and use the same controlled VS Code extension set in every fresh server; when present, the suite also requires activation diagnostics from every Extension Host and rejects extension activation failures. Missing File Search evidence makes a comparison non-qualifying, so an old Search-only profile cannot satisfy the release gate. Complete run files can be reused with `--resume`; an incomplete or interrupted run is rerun. `--preflight-only` writes `capacity-preflight.json` before enforcing the memory gate, so an undersized host still leaves auditable host/cgroup evidence. The default 50-session preflight requires 40 GiB of effective available memory. `--allow-low-memory` is explicitly exploratory and cannot produce a qualified 50-session result.

Workspace Agent Search never accumulates ripgrep stderr in memory. JSON input is capped at 2 MiB per line, and outbound events flush at either 128 matches or an estimated 256 KiB payload, whichever comes first; one oversized-but-valid line is sent alone. These bounds complement gRPC backpressure and request cancellation and prevent long source lines or repeated submatches from turning a streaming search into a multi-gigabyte batch.

Workspace Agent File Search uses the same 128-path/256 KiB streaming boundary. It preserves per-root include/exclude, gitignore, parent-ignore and symlink settings, classifies exact/fuzzy matches before crossing gRPC, deduplicates absolute paths and stops the ripgrep child at the shared result limit. Shadow parity treats two capped result sets as cardinality evidence only because ripgrep traversal order is nondeterministic even between two consecutive Node runs; uncapped comparisons require exact set equality.

Workspace Agent Watch also has two explicit pressure boundaries. Native FSEvents/fsnotify producers feed a shared non-blocking queue capped at 256 events; a slow gRPC consumer causes counted overflow instead of blocking the native callback or OS-event drain loop. The per-stream coalescing map is independently capped at 4,096 paths and an estimated 1 MiB encoded payload. Dropped events are surfaced through the existing watcher-overflow protocol. Normal RPC shutdown synchronously stops the parent-process monitor and waits for `GracefulStop`, so an embedded invocation does not leave ticker or shutdown goroutines behind.

The Node adapter bounds the pre-authentication ready-announcement line at 64 KiB and removes its stdout/process listeners on success, failure or timeout. Child exit waits also remove their listener when the deadline expires. Restart callback deduplication uses a single monotonic attempt number rather than retaining every historical attempt in a `Set`. Explicit Search cancellation and final shared-Watch release synchronously remove the gRPC stream from diagnostics before calling `cancel()`, so cleanup does not depend on grpc-js emitting a later `error` or `end` event.

The manually triggered `Workspace Agent capacity qualification` workflow fixes the release workload at 50 sessions and three runs for each variant. It targets a dedicated Linux x64 self-hosted runner carrying all four labels `self-hosted`, `linux`, `x64` and `workspace-agent-capacity`; the label selects the capacity pool, while the preflight independently rejects a runner with less than 40 GiB effective available memory. The dispatch requires the exact expected Content Search result and the Quick Open query/result, never passes `--allow-low-memory`, uses a unique output directory per run attempt and uploads the preflight, six raw JSONL profiles, logs, suite state and comparison report for 30 days. A failed preflight still uploads its report.

`smoke:workspace-agent:product` is the release-path functional and crash-recovery gate. It creates a temporary workspace, starts the compiled production client/server with Watch, Content Search and File Search enabled, drives one real Chromium session, verifies exact Search results, uses Quick Open to select a nested Markdown file and proves its content opened, then verifies Explorer add/delete events. It asserts one platform-correct Agent with no Node watcher fallback. It then terminates that Agent, requires the current Watch connection to converge to exactly one Node watcher, proves a later Search starts a different Agent PID, and verifies add/delete events still use the originally requested workspace path even when the native watcher resolves a symlink or the macOS `/var` alias. Two more Agent terminations exercise the full restart budget: the second on-demand Search must start a third unique PID, the third failure must report `exhausted`, and an exact Search must still complete through Node without launching another Agent. The gate checks `/readyz` at every active, fallback, recovered, exhausted and post-browser-close boundary: PID/state/restart evidence must match the process tree, readiness must remain non-gating, and all Agent streams must reach zero after browser cleanup. Browser close must reclaim the fallback watcher, Extension Host and PTY; Server close must reclaim the port. Schema 6 retains the Search input-remount retry evidence from schema 5 and adds the actionable File Search result and latency. Evidence is written under `output/workspace-agent` and `output/playwright`; Linux and Windows CI run the same path and retain the JSON/screenshot artifacts. The native package job also retains the verified binary and manifest for macOS, Linux and Windows. This gate is one-session functional acceptance, not the 50-session capacity result.
